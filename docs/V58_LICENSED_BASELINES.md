# V58 licensed notebook reuse and local baselines

## Narrow source-reuse reading

Kaggriculture’s official Rules separate the data license, winner license, open-source requirement, replay availability, and originality warranty. Competition-Specific Rule 2.7 labels **Data Access and Use: Apache 2.0**; Rule 2.4(a) allows Competition Data to be used for any purpose, while 2.4(b) restricts transmitting or redistributing Competition Data to non-participants. Rule 2.11 says replays may be public and downloadable and include a submission’s actions. Rule 2.5 specifies a CC-BY 4.0 winner license. General Rule 2.8(c) says open-source code used to generate a submission must use an OSI-approved license without a commercial-use limit. Rule 3.14 requires the submission to be the participant’s original work and the participant to warrant sole/exclusive ownership or rights and authority to grant required licenses. These texts appear together on the [official rules page](https://www.kaggle.com/competitions/kaggriculture/rules); the project captured the public page through Kaggle’s official PageService on 2026-09-26, with rules-content hash in [`source_manifest.json`](../experiments/v58_rights/source_manifest.json).

Each audited Kaggle notebook page separately says it is released under Apache License 2.0. For code the author owns or is authorized to license, Apache 2.0 grants broad reproduction, modification, and distribution rights subject to its conditions. Apache §4 requires recipients get the license, modified files carry prominent change notices, source-form copyright/patent/trademark/attribution notices be retained, and any applicable upstream NOTICE attributions be retained. [Apache License 2.0, §4](https://www.apache.org/licenses/LICENSE-2.0.html). Kaggle’s [Terms of Use, §9](https://www.kaggle.com/terms) gives other service users rights to access and use a public submission only as permitted by service functionality; the notebook’s explicit Apache notice is the stronger source-specific code license.

The notebook statement does **not** establish that the notebook author owns every embedded artifact. Ahmed’s V43 source attributes action schedules and shop routing to other contributors. Yusuke Hayashi’s notebook publishes a generated 719-turn action tape but does not state that tape’s provenance in the notebook text. Kaito’s notebook names the replay episodes that supplied its exact medoids. The competition replay clause permits availability and download; it does not expressly say that another player’s complete actions may be relicensed by a notebook author, copied into a new policy, or distributed as an agent. The existing project assessment treats that point as unresolved; see [`V58_REPLAY_RIGHTS.md`](V58_REPLAY_RIGHTS.md). Thus, Apache licensing is enough to adapt the licensed author-owned software components under its terms, but it does not by itself resolve third-party trace rights or the separate Rule 3.14 originality/ownership warranty. This is a source reading, not a legal opinion.

The practical separation is: use Apache-licensed observation-processing, accounting, or market-order code only after verifying its notices and contribution lineage; write a new action generator that derives each action from the live observation; exclude fixed 719-turn action schedules, replay medoids, and seed/episode lookups. If a route tape is integral to a proposed adaptation, seek a license from its actual rights holder or Kaggle clarification before any submission. A source license does not guarantee that a derivative satisfies competition eligibility.

## Recommendation

None of these three pinned public leader sources beat the frozen reset in its available fresh smoke comparison, and all three have replay/action-route dependencies. Do not use them as route candidates or ensemble their taped segments. Ahmed V43 has attributable observation-conditioned components around warehousing, terminal sales, market budgets, and shop-conditioned routing; those code modules are Apache-licensed in the notebook, but reuse should be limited to clearly identified author-owned code with the retained notices, and should be wrapped around an independently designed observation-only planner. The stronger research direction is an original resource/route controller with a small, separable market-guard seam—not a transplant of any of these agents. The 95000–95004 larger panel was not completed and is not warranted for these tape opponents.

## Separable observation-driven economic modules

A static pass over Ahmed V43’s pinned `main.py` found several local mechanisms that accept the current observation and a proposed action. They are possible postprocessors for a new RL hierarchy; none is a standalone route planner, and no gain estimate below is backed by an isolated ablation. The larger opponent matrix was stopped, and this source scan did not execute tape code or launch games.

| Source module | Interface in pinned V43 | Observation-based operation | Likely effect / integration caution |
|---|---|---|---|
| `EXP277 _r148_overflow(obs, action)` | Returns an updated `action` dictionary; final-hour only. | Projects the candidate actions, shed stock, ordered worker returns, and overnight capacity. It adds sales only for goods otherwise lost, then requires the entire final warehouse vector to match the original proposal. The source labels this an original Ahmed EXP277 contract. | Can reclaim some terminal-of-day overflow value without changing next-day inventory. Likely bounded and dependent on available market slots and sale prices. Rebuild its projection around the RL policy’s own proposed action; do not import the tape-bound parent/chassis. |
| `EXP277 _r148_atomic(obs, action)` | Returns candidate farmer/hand commands after seed-feasibility repair. | Counts current PLANT requests, simulates actor order using current seeds/tiles, and replaces impossible requests while keeping requests that can execute. It relies on a separate final-hour crop/watering safeguard. | Could reduce no-op seed actions and retain productive parallel plants. Port the validity check against the current observation and the RL hierarchy’s chosen batch; re-audit the last-hour safeguard separately. |
| `EXP231 _r97_budget(obs, orders)` | Boolean feasibility check for current `market` orders. | Calculates current-turn HIRE, BUY_LAND, BUY_PRODUCT, BUY_ANIMAL, and BUY_SEED cost from current cash and item-price estimates; intentionally credits no same-turn sale proceeds. | Useful hard constraint for a policy head that proposes an order list; can prevent overspending and infeasible purchase sequences. It should be recalibrated against the pinned engine and the RL policy’s reserve state. |
| `_r37_quote_priority(obs, order, stock)` + `_r37_reorder_sales(obs, action)` | Scores an individual SELL and reorders contiguous distinct SELL blocks in a proposed action. | Reads current public market inventory/params, own projected shed, and visible rival ripe yields; uses a conservative 8–24-unit competitor batch scenario to estimate price impact. It preserves order quantities and purchase barriers. The adjacent source comments attribute a capability transfer to lucifer19 and market functions to Kaggle Environments. | Could improve marginal realized sale value when order slots compete under a price curve. Expected benefit is uncertain and probably modest. A fresh planner should use official engine price state/params and implement its own pure scoring function; the V43 stock projection helper is attached to the route chassis. |

The route-coupled V43 functions are excluded from this shortlist: `_r36_reserve` walks `_IMPL.chassis.routes`; `_r97_supply` reads next and following route steps; `_r124_seed_budget` depends on route-derived reserve state; `_r128_service` and `_r128_credit_supply` query `_r128_future`; `_r148_seed_prefund` also queries planned future actions. The Yusuke notebook’s native policy chooses a tape plus one short shop-conditioned branch; its SixDay budget guard funds tape segments. Neither is a clean replacement for an RL resource head.

A clean integration boundary for the forthcoming original policy is:

```text
observation -> RL hierarchy -> proposed current farmer/hands/market action
             -> economic_guard(observation, proposed_action, reserve_state)
             -> feasibility / seed / storage / market-order checks -> action
```

Keep each check local to the current observation, current proposal, and explicitly maintained reserve state. Measure each guard separately against the unguarded policy with action-effect rate, cash, feed completion, and inventory/overflow diagnostics. Never let a guard retrieve an episode ID, select a recorded route, or consult a copied future-action schedule.

For any code adaptation, carry the original Apache LICENSE, retain every relevant contributor/source notice and applicable NOTICE, mark modified files, and keep source links and hashes in the module manifest. The V43 notebook itself lists substantial upstream lineage beyond Ahmed; use only components with traceable attribution. Whether the resulting full competition entry can satisfy Rule 3.14 remains separate from the code license.
